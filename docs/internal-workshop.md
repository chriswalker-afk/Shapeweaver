# PR21 — Internal level workshop

## Launch
Run `npm run workshop` from a checkout of this repository and open `http://127.0.0.1:4173/workshop/index.html`. The existing server remains loopback-only. The workshop is deliberately outside src/ and excluded by the production build's explicit allow-list. The normal development server does not serve it; `--workshop` enables its directory. This is a development tool, not authentication or an online shared editor.

## Author a draft
1. Start from a blank floor or load a copy of a released level. Copies have a workshop-prefixed ID and do not mutate campaign definitions, invoke the scripted level hints or write student progress.
2. Choose a palette item and click the coordinate canvas to place it. Drag existing items with 1, 0.5 or 0.1 unit snapping. The item list is an alternative to pointer selection. Spawn and portal are editable but not deletable.
3. Use the selected item's JSON inspector for precise vertices, centre/hinge, scale limits, support, permissions, and mechanism link IDs. Templates include terrain/water, beams, gates, crates/barrels, ladders, wedge, mushroom, compound key, checkpoint, linked gates, pressure plates, hinge and shape sockets, and decoration. Templates with links may initially be invalid; set their linked object/gate IDs and pivot properties before validation. Use room-data JSON for bounds, title, ID, chapter, bulk changes, and import. There is no dedicated per-vertex drag handle or full graphical mechanism form yet; exact JSON editing is intentional for developer flexibility.
4. Validate the draft. Structural limits: 150 x 100 maximum world extent, 100 authored items, 48 vertices per polygon, finite bounded coordinates and unique item IDs. Runtime validation reuses the actual polygon/object/room/mechanism validators, derives plate/socket gate state, rejects solid/hazard overlaps of interactive objects and unsupported initial objects, checks spawn/exit/checkpoints for real clear dry support. Terrain may touch/overlap other terrain. Invalid geometry can be edited but cannot enter playtest.
5. Start a playtest. The canvas uses the actual renderer, grid, reference overlay, full-path spell validators, immutable transformation commits, player physics, checkpoints and recovery history. Start paused. Select the object and type, enter actual mathematical parameters, Preview then Apply. Movement uses the normal keyboard/touch control module. Run/pause explicitly, or use developer fixed-tick stepping (120 ticks/s) to reproduce exact input sequences. Playtesting does not require using a particular spell or target move count. Undo and Return are recorded. Reset starts a new attempt from the draft.

## Proof and export
The recording stores interleaved cast and movement actions (run-length compressed fixed ticks, one-shot jump, horizontal/climb input), plus undo/return actions. Rejected previews/casts are not committed. The original room snapshot is kept separate from transformed playtest state. When the player reaches the portal, the verifier creates a fresh world and independently executes every action using the same game engine. A successful proof contains version 1, room, actions and a reproducible result summary. It is not a screenshot or a trusted "completed" flag. Imported bundles are replayed before acceptance. A change to the draft invalidates the previous proof; simply returning to edit does not change the original geometry. Export only a successful verified bundle. No custom level is added to the campaign automatically.

`npm run verify:level -- path/to/export.verified.json` gives a non-zero exit code on bad geometry, invalid action, failed completion or mismatching result. Import and CLI limit file size to 2 MB; replay limits are 36,000 physics ticks (five simulated minutes) and 4,000 actions. Export/import is local JSON only. A replay proves that at least one path works, not optimality, absence of shortcuts or appropriate difficulty.

## Verification and boundaries
Tests exercise all twelve PR20 recorded routes through the workshop recorder/verifier, interleaved movement/casts, undo/return, malformed/unfinished proofs, draft edit isolation, mechanism templates, CLI and serving/build isolation. Chromium tests cover pointer placement/dragging, property validation, actual spell preview/commit, exact stepping, verified export, re-import and edit invalidation at desktop and compact viewport sizes. Existing campaign regression and browser QA remain in place. Human visual and real-device review remain necessary. No student-facing workshop, custom library or backend, no deployment/domain changes.

PR24 adds waterwheel rotor and external-centre walkway templates. A rotor uses a solid polygon, fixed hinge on/in the polygon, rotation-only permissions and hinged support. The walkway uses a finite `fixedCentre: [x,y]` strictly outside the polygon but inside room bounds, rotation-only permissions and enchanted support. Dragging either template in the editor moves its reference centre along with its geometry; the exact property inspector can reposition that centre separately. During play the centre is fixed. Guide rings and dotted radial lines are non-solid. The full-arc validator governs the actual moving polygon.

PR25 adds a dual-purpose bridge ladder template. Set `bridgeDeck: true` on a rectangular ladder with translation and rotation permissions. A horizontal deck is solid; upright geometry is climbable and non-solid. The marked pivot moves with translations. The common campaign fixture format supports `segments`, one movement route after each cast, and the workshop tests record those actions in their real order.
