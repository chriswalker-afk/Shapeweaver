# PR42 — CI performance optimisation

## Measured baseline
PR41's successful Browser QA (run 46149277169, commit 6896e0d): the full sequential campaign step took approximately 153 seconds, Chromium setup 31 seconds, production smoke 11 seconds, home acceptance 10 seconds, library acceptance 11 seconds, workshop QA 4 seconds and screenshot uploads 7 seconds. The combined browser archive was 118,273,554 bytes and duplicated the home and library screenshot archives. These are observed step times, not the new workflow's measured performance.

## Changes
- Four independent matrix jobs each run the same 36 actual browser cases at one of the four original viewport sizes, including all existing navigation, spell, stage, toggle, hint, and runtime-error assertions. Four jobs run concurrently where runner capacity permits; failure does not cancel the other shards.
- A separate concurrent focused job runs both hosting-path smoke tests, all 13 home layout/progress cases, all eight library layouts and workshop QA. The final job keeps the previous browser-smoke check name and fails if any dependency fails, is skipped or is cancelled. It downloads only the small per-shard JSON artifacts, checks their commit identity and successful completion, verifies all 144 distinct level/viewport pairs and four complete home showcase records, and publishes the combined report. Missing, malformed, duplicate or wrong-viewport evidence cannot produce a successful gate.
- Cache the optional pinned Playwright Chromium browser download using OS, architecture, runner image and Playwright version. System dependencies still install on each runner. The existing Pages build seeds the same versioned browser cache on main after PR42 merges; a first cold run or a new browser version can miss the cache. The deployed runtime and its dependency-free artifact are unchanged.
- Ordinary PRs keep menu/focus/showcase screenshots, plus initial/preview/cast/ready screenshots from all four tutorials, the first puzzle of each later chapter, and the finale (11 representative levels per viewport). Failures capture the current browser state where possible, even for unsampled levels. All 36 levels still execute every assertion regardless of screenshot mode. Manual workflow dispatch with full_screenshots enabled retains every original campaign capture. The local default likewise remains full.
- Retain complete home and library review artifacts. Keep screenshot archives separate per viewport and for production/workshop, avoiding the previous duplicate combined upload. shapeweaver-browser-qa is now a small combined JSON report. In a rerun, same-name artifacts are overwritten, so old screenshot/report names do not conflict. All report validation is against the same workflow commit.
- A newer commit cancels the obsolete browser workflow on the same ref. It never bypasses required checks for the current commit.

## Validation and trade-offs
Run Scaffold CI and Browser QA on PR42 before merging; compare the longest concurrent job plus final gate with the previous wall-clock time. The aggregate report records per-shard elapsed time and successful screenshot counts. Unit tests cover option parsing, representative coverage, exact union, actual report-aggregation CLI with failing fixtures, and ensure the workflow matrix matches the canonical viewport definitions. A full screenshot dispatch remains useful for comprehensive aesthetic audits.

Parallel jobs can consume more total runner minutes even when wall-clock feedback improves; job scheduling/queueing, shared runner limits and cold caches affect results. No speed-up figure is promised before the actual PR42 run completes. No change to branch protection, campaign maths, gameplay, UI, saved progress, version or required workflow success. After PR42 merge, verify the Pages deployment (now using the same cached-browser setup).
